## 1. Executive Summary

The 2026-07-13 verified report left one row explicitly unresolved: "Foundry Workflow Agent — Not independently characterized this pass... Inferred, low confidence." This pass closes that gap using two Microsoft Learn pages fetched live today, plus this project's own captured deployment code — **not** the generic "Hosted Agents get Entra identities" inference the prior report was forced to lean on.

**The gap is now Confirmed, not inferred, and it turns out to be a two-layer problem, not one.** Microsoft's `authentication-authorization-foundry` page (fetched live today; page metadata `updated_at: 2026-06-19`) contains a Feature Support Matrix stating in plain text: **"Agents service | API key: No | Microsoft Entra ID: Yes."** This is Microsoft's own primary documentation, not a secondary inference from Hosted Agent design patterns — and it applies to the Agents service generically, with no split between Prompt/Workflow/Hosted subtypes. Separately, `agents/concepts/agent-identity` (fetched live today; `updated_at: 2026-07-01`) describes a distinct, deeper mechanism — how an already-invoked agent authenticates *outbound* to its own tools (MCP servers, A2A endpoints) via a four-stage OAuth token exchange using "agent identity blueprints." This second mechanism is about tool-calling, not client invocation, and was conflated in earlier framing — this report separates the two clearly (Section 2).

**Grounding it in this project's actual deployment removes the last bit of inference.** This project's own captured SDK script (`foundry-capture/workflow.md`, captured 2026-05-14 as a precaution against an anticipated wipe that never occurred) shows the *only* way the `safe-agents` Workflow Agent was ever successfully invoked was `AIProjectClient(endpoint=..., credential=DefaultAzureCredential())` followed by `openai_client.responses.create(extra_body={"agent_reference": {"name": "safe-agents", "version": "41"}}, ...)`. There is no API-key branch anywhere in that code. This matches Microsoft's matrix exactly and is independent, first-party proof — not a vendor claim being taken on faith.

**For SPLX specifically:** a live re-fetch of `docs.probe.splx.ai/ai-red-teaming/probe/target/index` today reconfirms the connector list is unchanged from the 2026-07-13 pass — still no connector named for Foundry, Foundry Agent, or Workflow Agent, and (new observation this pass) even the closest-fitting connector, **Azure OpenAI**, has no config field for the `agent_reference`/workflow-name/version parameter this project's own workflow invocation requires. So even setting auth aside, the Azure OpenAI connector's shape cannot select a workflow at all — it only knows how to select a model deployment. This closes the "would the OpenAI Assistant connector maybe work anyway" open question from the prior report indirectly: neither of SPLX's two most Azure-relevant connectors has the right shape, for two independent reasons (auth on one axis, missing config field on the other).

**Single most actionable recommendation:** Scan the Claude 4.6 model deployment directly via SPLX's Azure OpenAI connector now — that path is unaffected by anything in this report and remains the same-day, zero-engineering option. But **flag explicitly to whoever commissions the scan that this only tests the model+system-prompt layer**, not the Supervisor→Preparer→Reviewer→Formatter orchestration, the review loop, the HITL question node, or JSON-schema enforcement — which is where this project's own build sessions found the actual interesting failure modes (guardrail triggers tied to `tool_choice: required`, orchestration-language prompt bleed, Table-vs-String output type gotchas). Reaching the full workflow requires the REST API connector plus a proxy built to the exact spec in Section 4 — a concrete, buildable design now, not a generic pattern, because it's grounded in this project's own working code.

**Operational gap, now resolved:** this project's own capture files disagreed with each other about the endpoint. `workflow/foundry-capture.md` (dated 2026-05-06) references project `AI-Agent-Safety` at endpoint `Aldo1.services.ai.azure.com`. `foundry-capture/workflow.md` (dated 2026-05-14) references `tatum-safeagents-resource.services.ai.azure.com`, project `tatum-safeagents`. **Resolution (confirmed by project owner, 2026-07-14): the correct target is `tatum-safeagents-resource` / `tatum-safeagents`.** The `Aldo1` / `AI-Agent-Safety` endpoint is a *separate, unrelated* Foundry project not used for this work — it was one of two hypotheses floated earlier (unrelated project vs. resource rename), and the "unrelated project" hypothesis is the correct one. This also retires the earlier speculation that `Aldo1` was "if anything the more likely still-accurate one" — it is not. Use the `tatum-safeagents` values for all proxy/scan configuration. Liveness of the workflow at that endpoint should still be sanity-checked operationally (Azure Portal / `az` CLI) immediately before a scan run, but the address ambiguity is closed.

## 3. The Auth Problem, Precisely Stated (Two Layers, Not One)

The 2026-07-13 report and handoff pack both described "the Entra problem" as a single undifferentiated barrier. Today's primary-source fetches show it is structurally two separate mechanisms, and only one of them is what actually blocks SPLX:

**Layer 1 — Client-to-Agent invocation (this is what blocks SPLX):**
Per the Feature Support Matrix in `authentication-authorization-foundry`: the "Agents service" row is API key: **No**, Entra ID: **Yes**. This governs how *any external caller* — a human, a script, or a scanner like SPLX — invokes a Foundry agent or workflow at all. There is no API-key path into the Agents service, full stop. This project's own SDK script proves the practical shape of the only working path: `DefaultAzureCredential()` acquiring a token scoped to `https://ai.azure.com/.default`, then calling `responses.create()` with an `agent_reference`. **This is the layer SPLX's connectors cannot reach**, because none of SPLX's connectors (Azure OpenAI, OpenAI Assistant, REST API) have a documented Entra/OAuth2 client-credentials acquisition flow built in — the REST API connector's "OAuth is also an option" language remains the only thread of possibility, and remains untested (carried forward as an open question, Section 6).

**Layer 2 — Agent-to-tool outbound authentication (not what blocks SPLX, but relevant if the workflow is later found to use MCP/A2A tools):**
Per `agent-identity`: once an agent *has been invoked* (Layer 1 already succeeded), and it needs to call an external tool (Azure Storage, an MCP server, an A2A endpoint), Foundry runs a separate four-stage token exchange — blueprint authentication → agent identity token issuance → scoped token request → authenticated tool call — using "agent identity blueprints" that can be backed by a client secret, certificate, or (recommended) a federated credential trusting the project's managed identity. This is entirely internal to Foundry's trust boundary and invisible to an external caller. **It does not add a second external barrier for SPLX** — it only matters if you were designing a proxy that itself needed to impersonate a tool the agent calls, which is not the scanning scenario here. This project's workflow uses `file_search` (a built-in Foundry tool, not MCP/A2A), so Layer 2's supported-tools list (MCP, A2A only, per the agent-identity doc) doesn't even apply to this project's current tool configuration.

**Net effect:** a scanning proxy only needs to solve Layer 1. It needs one credential-acquisition flow (service-principal client-secret, matching the existing REST-API-proxy spec from the 2026-07-13 report) to get a token scoped to `https://ai.azure.com/.default`, then call the workflow exactly as this project's own script does. Layer 2 is Foundry's internal problem to solve, not the proxy's.

## 4. Concrete Proxy Spec for Scanning `safe-agents` Specifically

> **Try the config-only path first (see Gap #2, updated).** The SPLX REST API doc (source #12) confirms the connector's OAuth form has the client-credentials fields Layer 1 needs. If that OAuth flow authenticates *and* a payload template can carry the `agent_reference` parameter (step 4 below), you may not need to build this proxy at all — or only a thin routing shim. Build the full proxy below only after the OAuth test shows what's actually missing.

This refines the 2026-07-13 report's generic REST-API-proxy spec (its Section 5) into a spec anchored to this project's actual working code, removing the remaining guesswork:

1. **Acquire a token.** Use a service-principal client-secret or certificate (simplest) — or a managed-identity-based flow if the proxy itself runs as an Azure compute resource — to call `DefaultAzureCredential().get_token("https://ai.azure.com/.default")`, exactly as this project's own SDK script does. Refresh on a schedule; a Probe scan firing thousands of requests over an extended run will outlast a single token's TTL.
2. **Construct the client.** `AIProjectClient(endpoint="https://tatum-safeagents-resource.services.ai.azure.com/api/projects/tatum-safeagents", credential=<token-provider>)`. **Confirmed target (see Section 6, Gap 1 — resolved):** use `tatum-safeagents-resource` / `tatum-safeagents`. The `Aldo1` / `AI-Agent-Safety` values are a different, unrelated project — do not use them. Sanity-check liveness operationally right before a scan run.
3. **Accept SPLX's REST API connector payload.** Per the 2026-07-13 report's Section 5, SPLX substitutes `{message}` and `{session_id}` into a configurable payload template. The proxy's HTTP handler receives this, extracts the attack prompt.
4. **Invoke the workflow exactly as the captured script does:** create a conversation via `openai_client.conversations.create()`, then `openai_client.responses.create(conversation=conversation.id, extra_body={"agent_reference": {"name": "safe-agents", "version": "<current-live-version>"}}, input=<attack prompt>, stream=True)`. Use `{session_id}` to map to `conversation.id` if session continuity across attack turns is needed, or create a fresh conversation per `{message}` if not.
5. **Reconstruct a single reply.** Consume the streamed events — filter for `RESPONSE_OUTPUT_TEXT_DONE` (per this project's own event-handling code) to get the final text, ignoring intermediate `workflow_action` events (which represent internal Supervisor/Preparer/Reviewer/Formatter step transitions, not the user-facing reply). Note: this project's workflow includes a **Question node** ("Is this acceptable?") that pauses for human input mid-workflow under some paths — a scanning proxy will need to auto-respond to this (e.g., always answer "yes"/blank) or the workflow will stall waiting for a human turn that will never come during an automated scan. **This is a new finding this pass**, not covered in either prior report, and is a concrete blocker a proxy must handle, not just an auth detail.
6. **Return JSON at a stable path** (e.g., `{"reply": "<extracted text>"}`) so SPLX's Response Path field can be set once.
7. **Clean up:** `openai_client.conversations.delete(conversation_id=conversation.id)` per-scan-turn, matching the captured script's own cleanup behavior, to avoid leaving orphaned conversation state in the project.

**What this spec resolves that the 2026-07-13 report couldn't:** the exact SDK call shape, the exact auth scope string, and — newly surfaced this pass — the HITL Question-node stall risk, which is specific to this project's workflow design (the sequential + review-loop + HITL pattern) and would not appear in a simpler Prompt Agent or Hosted Agent target.

## 5. What a Model-Only Scan Would and Wouldn't Cover (Scoping Honesty)

Per the 2026-07-13 report's recommended pilot path, the fastest available step remains pointing SPLX's Azure OpenAI connector at the Claude 4.6 model deployment directly. Grounded in this project's own build history, here is what that would and wouldn't actually validate:

| Would cover | Would NOT cover |
|---|---|
| Prompt injection resistance of the model + whichever single agent's system prompt is loaded into the test deployment | Cross-agent orchestration (Supervisor→Preparer→Reviewer→Formatter handoff integrity) |
| System prompt leakage resistance | The review loop's turn-count logic and its "force approval after turn 2" Power Fx condition |
| Baseline jailbreak/off-topic behavior of the raw model | The HITL Question node and whether it can be manipulated to skip/auto-approve |
| — | The `tool_choice: required` + `file_search` guardrail-trigger interaction this project's own Session 2 testing identified as the dominant real-world failure mode (7/10 flag rate on Claude) |
| — | Whether Formatter's JSON-schema enforcement can be broken via injected content passed through from upstream agents |
| — | The confirmed content-filter masking risk (Section 2 above) — since it can only be observed by comparing multi-turn/multi-agent behavior, not a single model call |

This table is the single clearest artifact for explaining to a stakeholder why "we ran a SPLX scan" and "we validated the safe-agents workflow" are not the same claim unless the proxy in Section 4 is actually built.
